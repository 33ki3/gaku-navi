# コメント規約

## 配置

- **ファイル先頭**: 処理を持つファイルには、扱う内容・責務と関連処理との関係が分かる概要を付ける。新規ファイルにも周辺ファイルと同じ粒度で記述する。単純なマスタ行や再エクスポートには不要。
- **処理内**: 複数段階の計算・候補選定・探索には、条件の準備、除外判定、固定分の差し引き、集計・評価などのブロック直前に、目的と理由が分かるコメントを付ける。JSDocだけで済ませず、周辺ファイルの粒度に合わせる。
- **公開シンボル**: 利用側だけでは責務や制約が分かりにくい export に JSDoc を付ける。名前だけで明らかな小さなコンポーネントや単純な再エクスポートには不要。
- **関数**: 引数、戻り値、副作用が複雑な関数に `@param` / `@returns` を付ける。単純なイベントハンドラーへ定型文を増やさない。
- **非公開ヘルパー**: 名前で目的が明らかならコメントしない。検証・保存・復元など理由が必要な処理だけ説明する。
- **インライン**: 論理ブロックの直前に、分岐条件、データを守る理由、UI 制約を書く。
- **公開値・フィールド**: API 契約として集約する `as const` object は、各 entry に用途が分かる短いコメントを付ける。外部へ渡す request / response や runtime schema は、フィールドごとに意味・制約を説明する。識別子や値の単なる言い換えは避け、内部型の自明なフィールドには定型コメントを増やさない。
- **テスト**: `describe` / `it` で振る舞いを示し、フィクスチャや比較理由が分かりにくい場合だけコメントする。

## 文体

- コメントは日本語で書く。
- 一文だけなら末尾に `。` を付けない。複数文は `。` で区切る。
- 120文字以内の短いコメントは1行にする。長い場合は句点や意味の境界で折り返し、語、括弧、引用、識別子の途中では分割しない。
- Prettierはコメント内の既存の物理改行を自動で結合しないため、120文字以内でも手動改行が残る場合は編集時に1行へ戻す。
- 既存ファイルを変更するときは、同じディレクトリの記述粒度へ合わせる。

## JSX

return 内に複数の主要コンポーネントがある場合は、必要に応じて直前へ `/* サポート詳細モーダル */` のような短い名詞句を置く。レイアウト要素や map 内の各要素へ重ねて書かない。既存の責務コメントは、整理や分割時に適切な移動先へ引き継ぐ。

## 禁止事項

- 現在の処理の責務・制約・理由を説明する。変更前との比較やレビューへの返答を処理コメントに書かない。
- レビュー返信や対応報告をコードコメントに書かない。
- `Q:` / `TODO:` はコードから削除し、必要な項目は `todo-management` に従って管理する。
- 実装を言い換えただけのコメントや、同じ説明の重複を追加しない。
