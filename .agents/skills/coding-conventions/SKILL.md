# gaku-navi コーディング規約

プロジェクト全体で守るべきコーディングルールを定義する。
データ層のアーキテクチャ（types / constant / data の構造・命名規約）は **data-architecture** スキルを参照。
todo / archive の運用ルールは **AGENTS.md を唯一の正本** とし、この skill には重複記載しない。

1. **コーディング基本規約** — コメント・ファイル分割・リテラル禁止
2. **import 規約** — namespace import パターン
3. **コメント規約** — JSDoc の書式
4. **ベストプラクティス** — デッドコード検知

---

## 1. コーディング基本規約

- **コメント**: 小学生でもわかるレベルでわかりやすく書く。何をしているか・なぜそうするかを日本語で。
- **ファイル分割**: 行数だけを基準に分割しない。責務の境界、再利用性、テストのしやすさが改善する場合に分割を検討する。大きなマスタデータやテストは、行数が多くても一つの責務なら無理に分割しない。
- **文字列・数値の比較**: 複数箇所で共有するドメイン値や仕様値は `src/types/enums.ts` や `src/constant/` の定数を使用する。DOMイベント名、単発のレイアウト値、テストフィクスチャなど、局所的で意味が明らかな値まで機械的に定数化しない。
- **enum 値の参照**: `as const` パターンで定義された enum 相当の値は定数経由で参照する。ドメイン上の値を意味のない数値・文字列リテラルで繰り返さない。

```ts
// ✅ OK
{ uncap: UncapType.Zero, level: 40 }

// ❌ NG
{ uncap: 0, level: 40 }
```

## 2. import 規約

### namespace import（コンポーネント / hooks / utils）

外部から data 層と constant 層にアクセスする場合は **namespace import** を使う:

```ts
import * as data from '../data'
import * as constant from '../constant'
import * as enums from '../types/enums'
```

### type-only import

型としてのみ参照する場合は `import type` を使う:

```ts
import type { SupportCard } from '../types/card'
import type { RarityType } from '../types/enums'
```

### constant/ 内部の import

`src/constant/` と `src/data/` 内部のファイル間は **namespace import を使わず直接 import** する:

```ts
// constant/ → types/
import { RarityType, UncapType } from '../../types/enums'

// constant/ → constant/
import { BADGE_ABILITY_GRID } from './styles'
```

### 直接 named import が許可されるケース

- `src/constant/` および `src/data/` 内部のファイル間参照
- `src/types/` からの型 import
- 循環参照回避が必要な場合
- namespace import と直接 import の併用

## 3. コメント規約（JSDoc / インラインコメント）

コメントは、ファイル・公開API・処理ブロックの3段階で役割を分ける。
同じ内容を複数のコメント形式で重ねず、コードだけでは分からない
「何をするか」と「なぜそうするか」を日本語で補足する。
変更履歴や質問への回答はコメントに残さず、`.github/todo/todo.md`で管理する。

### TypeScript

```typescript
// ===== ファイル先頭 =====
/**
 * ファイルの概要（何のファイルか）
 *
 * 補足説明があれば2段落目に書く。
 */

// ===== 関数 =====
/**
 * 関数の概要（何をするか）
 *
 * @param paramName - パラメータの説明
 * @returns 戻り値の説明
 */

// ===== interface =====
/** インターフェースの概要 */
export interface Foo {
  /** フィールドの説明 */
  bar: string
}

// ===== 定数 =====
/** 定数の説明 */
export const FOO = 42
```

### 共通ルール

1. **ファイル先頭**: 複数の責務を持つファイル、外部副作用を持つファイル、
   データ形式を定義するファイルには、1つだけ概要を書く。
   単純なマスタ行や短い再エクスポートだけのファイルには説明を重ねない。
2. **公開シンボル**: exportするコンポーネント、hook、utility、型、enum、共有定数のうち、
   利用側だけでは責務や制約が分かりにくいものにJSDocを付ける。名前だけで意味が明らかな
   小さなコンポーネントや単純な再エクスポートへ定型コメントを増やさない。
3. **引数と戻り値**: exportする関数・hookと、引数や副作用が複雑な関数は
   `@param`と`@returns`を付ける。引数がない・戻り値が`void`の単純なイベントハンドラーへ
   定型文を増やさない。
4. **非公開ヘルパー**: 関数名で目的が明らかな小さな処理はコメント不要。
   再利用される処理、検証・保存・復元など理由が必要な処理はJSDocまたは直前の`//`で説明する。
5. **インラインコメント**: 関数内の論理ブロックの直前に`//`で記載し、実装の逐語訳ではなく
   分岐条件・データを守る理由・UI上の制約を説明する。
6. **テスト**: `describe`/`it`で期待する振る舞いを明示する。ファイル先頭の説明は、テスト対象の境界や
   テストデータの前提がコードだけでは分かりにくい場合に付ける。
   setupやassertのコメントは、テストデータの意図・再現している不具合・値を比較する理由がある場合だけ付ける。
7. **日本語と句読点**: コメントは日本語で書き、次の判定をすべての`//`・`/** */`・JSXコメントへ適用する。
   - コメントが一文だけで完結する場合は、末尾に`。`を付けない。例: `// 保存済みのカードを読み込む`
   - 一文の後ろに補足や別の文が続く場合は、文の区切りに`。`を付ける。例: `// 保存済みのカードを読み込む。壊れている項目は除外する`
   - 複数行のJSDocも同じ扱いとし、続きがある文は`。`で区切る。`@param`・`@returns`の説明は短い名詞句なら句点を付けない。
   - 既存コメントを変更するときもこの基準へ揃え、意味のない句点だけを残さない。
   - **折り返し**: `printWidth`（120文字）以内の短いコメントは1行にする。
     概要と補足、列挙、条件と理由など複数の意味単位がある場合、または120文字を超える場合だけ複数行にする。
     句点・列挙の区切り・条件と理由の境界で改行し、日本語の語や文の途中では切らない。
     `（）`・`()`・引用符・バッククォート内の文字列は途中で分割せず、開き括弧の直後でも改行しない。
     括弧内が長い場合は、括弧の前または括弧を閉じた後の意味単位で改行する。
8. **質問コメント禁止**: `Q:`・`TODO:`・回答文・レビュー相手へのメッセージをソースへ残さない。
   Qを削除した後に回答や判断理由をコメントとして置き換えることも禁止する。
   質問が必要なものは`.github/todo/todo.md`のQ&Aへ記録し、回答後もコードからは削除する。
   コードコメントは、利用者やレビュー相手ではなく、将来の保守者へ実装の責務・制約・理由だけを説明する。
9. **JSXコメントの基準**: return内で複数のコンポーネントを描画する場合は、各主要コンポーネントの直前に
   対象名や役割を示す短い名詞句のJSXコメントを置く。例: `/* サポート詳細モーダル */`。
   「〜を表示する」「〜を開く」のように動作を言い換える表現は避け、コメントは対象名だけで意味が伝わる長さにする。
   表示条件が重要な場合だけ「選択中のサポート詳細モーダル」のように対象名へ含める。
   `div`や`span`などのレイアウト用要素、同じ役割のmap内の個々の要素にはコメントを重ねない。
   既存の責務コメントを整理・分割時に削除せず、移動先へ引き継ぐ。
10. **既存ファイルとの統一**: 追加前に同じディレクトリの記述粒度を確認し、
    ファイル先頭・公開シンボル・論理ブロックの3段階を同じ順序で揃える。
    重複する説明は1か所へまとめる。

## 4. フォーマット（Prettier）

- **コミット前に必ず `npx prettier --write` を実行する。** フォーマット漏れは CI で検出されるが、事前に防ぐ。
- ファイル編集後は `npx prettier --check "src/**/*.{ts,tsx}"` で差分がないことを確認する。
- **対象**: CI と同じ `src/**/*.{ts,tsx}`（TypeScript ファイルのみ）。JSON・CSS 等は対象外。
- コメントは原則1行で記述し、`printWidth`（120文字）を超える場合だけ意味のまとまりで手動改行する。
  JSDocは概要・補足段落・`@param`・`@returns`をそれぞれ分け、JSXコメントは対象名や役割のまとまりで折り返す。
  括弧・引用・識別子の途中や文の途中では折り返さず、開き括弧の直後に続きの行を置かない。
  Prettierはコメントの文章を意味単位では折り返さないため、手動で整えてからコード全体をチェックする。
- Prettier の設定はプロジェクトルートの設定ファイルに従う（デフォルト設定）。

```bash
# 変更ファイルのフォーマット
npx prettier --write <ファイルパス>

# 全体チェック（CIと同じパターン）
npx prettier --check "src/**/*.{ts,tsx}"
```

## 5. ベストプラクティス

### フォールバック・デフォルト値ポリシー

- **原則**: フォールバック（`?? defaultValue`, `|| fallback`）は可能な限り排除する。データが存在しない場合はバグであり、フォールバックで隠さない。
- **テストで担保**: `masterData.test.ts` で enum × マスタデータの全組み合わせの存在をテストし、実行時フォールバックの必要性を排除する。
- **残してよいフォールバック**: 型上 `| null` や `| undefined` が必然の場合（例: 部分的に定義されたデータ、オプショナルプロパティ）。この場合は理由をコメントで記載する。
- **非 null アサーション `!`**: マスタデータのテストで全キーの存在が保証されている場合、`Map.get(key)!` は許可する。

### 型安全性

- **string 型を避ける**: 関数の引数・戻り値・オブジェクトのキーに `string` を使わず、enum 型（`as const` パターン）を使用する。
- **`as` キャスト制限**: `as SomeType` は **データ層**（`src/data/` 内の TS ラッパー）のみ許可。コンポーネントや utils では原則禁止。
- **i18n キー構築**: テンプレートリテラルによる動的 i18n キー構築は禁止。マスタデータまたは `effectLabelResolver.ts` 経由で返す。

### デッドコード検知・フォーマット

| ツール     | 用途                          | コマンド                                   |
| ---------- | ----------------------------- | ------------------------------------------ |
| Prettier   | フォーマット確認              | `npx prettier --check "src/**/*.{ts,tsx}"` |
| TypeScript | 型チェック・未使用ローカル・パラメータ | `npx tsc -p tsconfig.app.json --noEmit` |
| ESLint     | リポジトリ全体の静的解析                | `npm run lint`                          |
| knip       | 未使用 export・ファイル・依存           | `npx knip --reporter compact`            |
| Vitest     | テスト実行                              | `npm run test:run`                       |

### 一時ファイル・スクリプト

- **作業ディレクトリ**: 一時ファイルが必要な場合は必ずプロジェクトルートの `./tmp/` を使用する（git管理外）。
- **システム `/tmp` 使用禁止**: データ消失リスクがあるため、システムの `/tmp` は絶対に使わない。`pre-tool-check.sh` hook でブロック済み。
